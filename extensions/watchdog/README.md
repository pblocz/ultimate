Reports failed runs to their subagent owner, or to `defaultDestination` when there is no owner. If there is no usable recipient, or the recipient is the failed conversation, it records the failure and shows a notice without a new input. Idle branch reminders still go only to the optional coding coordinator.

A run fails with a provider error (`model_error`, `no_model`), or when restarts cut it off: the host stopped while the model was answering and no retry was left (`interrupted`), or the run was cut off Pi Durable's `restartLimit` times in a row (`restart_limit`). A run cut off by restarts is reported at once and never retried, because its last tool call may have partly run.

Provider errors classified as temporary by Pi, Claude Code relay responses that ended incomplete with status 200 or unknown, and model streams that stalled (`Model stream stalled: …`, which Pi does not retry by itself) get up to four continuations, after 1, 5, 15 and 30 minutes (`RETRY_DELAYS_MS`): a provider outage gets about 50 minutes to pass. Each continuation's request ID names the generation it continues (`watchdog-retry:<task>`); when that continuation fails too, the new report counts one more than the watchdog task it came from. A broken login (“not logged in”, a failed OAuth refresh, `invalid_grant`) is reported at once with a hint to log in again that names the provider (`diagnose` in `server.ts`). If the conversation is busy at that deadline, or ran again after the failure (even if that run failed too), watchdog leaves it alone. `subagent stop` cancels that child's pending watchdog task and withdraws any queued retry input, using the stop handler's captured identities so replay leaves later work alone. After the fourth failed continuation it reports, counting them (`retries`). Persistent and non-temporary errors become a `watchdog.failure` card with the conversation, title, error, last tool step and any login hint; reporting a subagent's failure marks its parent's `failed` action for it `given-up`. A standing agent that is its own failure recipient gets a `watchdog.standing-failure` card in its transcript. The card starts no turn. Pi Durable resumes the report task after a restart, and the same request ID prevents duplicate cards. Other self-reports remain notices. User Stops are ignored; reply-expecting Messages inputs already have a failure reply and are excluded. A `board.delivery` task that faults (the failure reply itself could not be sent) becomes a `watchdog.failure` card for the message's sender, with step `message delivery`. When the user sent it, the card goes to `defaultDestination`, else to the message's target; with neither, it is a notice.

A root receipt and background task are created atomically for each failed generation; retry/report submissions use stable request IDs. On open, missed failures are scanned above the stored high-water mark, never advancing past unfinished work. Fresh installation marks existing tasks as historical and reports none of them.

The `watchdog.idle` input note is only for @ultimate and only when its set of branch IDs changes. It excludes concluded, running (including owned children), recently active, user-question-waiting and lander-queued branches. A branch counts as idle after 30 minutes, since a coordinator that ended its run with nothing to wake it may have stalled; one with an open reply-expected message to another conversation gets two hours. It lists at most ten, and clears with “No branches are idle.” It never changes the system prompt.

Watchdog keeps the last 20 reported failures (`watchdog.reported` on the root, written with each report, including @ultimate's own) and serves them through `WatchdogApi.failures(since)`, newest first; the `status` extension reports them.
